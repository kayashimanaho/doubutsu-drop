Matter.jsをブラウザゲームに採用した理由

2026年7月3日

どうぶつドロップはブラウザだけで動く完全フロントエンドのゲームです。どうぶつたちが転がり・積み重なるリアルな動きを実現するために物理エンジンを使っていますが、「なぜMatter.jsを選んだのか」「組み込む際に何に苦労したか」を開発者の目線で振り返ります。

なぜ物理エンジンが必要だったか

合体パズルゲームを自前のコードだけで実装しようとすると、円同士の衝突判定・摩擦・重力・積み重なったときの安定化……と、物理シミュレーションに必要な計算が非常に多くなります。最初は「衝突したら位置を修正する」程度の簡易実装で始めましたが、すぐに限界を感じました。

問題のひとつがトンネリングです。小さなひよこが高速で落下したとき、フレームとフレームの間に床をすり抜けて消えてしまうことがありました。また、どうぶつが重なって積み上がるとき、お互いが振動してガタガタ揺れ続ける現象（スタック不安定性）も頻発しました。こうした問題を自力で解決するのは、ゲームロジック本体の開発とは別に相当な工数がかかります。既存の物理エンジンを使うことで、これらの問題をまとめて解決できると判断しました。

Matter.jsを選んだ理由

ブラウザ向けの2D物理エンジンはいくつかあります。代表的なものを比較した上でMatter.jsを選びました。

ライブラリ特徴どうぶつドロップへの適性
Matter.jsピュアJavaScript、依存なし、ドキュメント充実◎ 軽量で外部依存がない
Cannon.js / cannon-es3D物理が得意、WebGL向け△ 2Dゲームには過剰
Box2D（emscripten版）非常に高精度、ゲーム業界標準△ wasm読み込みのオーバーヘッドが大きい
Planck.jsBox2DのJSポート、軽量○ 候補に入ったが情報量でMatter.jsが上

決め手は「外部依存ゼロで使えること」と「日本語を含む情報量の多さ」でした。どうぶつドロップはサーバーレスで動くシンプルな構成なので、wasm（WebAssembly）のような追加バンドルなしにCDNから1ファイル読み込むだけで済むMatter.jsは、今回の要件に最もフィットしていました。

実装で直面した課題と解決策

1. トンネリング対策

小さな物体が高速で移動するとき、衝突判定フレームをすり抜けるトンネリングは、Matter.jsのデフォルト設定でも稀に発生しました。どうぶつドロップでの対処は2つです。

  • 床を200pxの厚みに設定する：見た目の床ラインは画面下部に描画しつつ、物理ボディとしての床は200px厚の矩形にしました。こうすることで、どんな高速落下でも床をすり抜けることがなくなります。
  • positionIterationsを増やす：衝突解決の反復回数をデフォルトの6から10に増やし、衝突の精度を高めています。処理コストはわずかに増えますが、現代のスマートフォンで体感できるほどの差はありませんでした。
Engine.create({ gravity: { y: 1.2 }, positionIterations: 10, // デフォルト6→10 velocityIterations: 8, // デフォルト4→8 })

2. 積み重なり時のガタつき抑制

どうぶつ同士が積み重なったとき、お互いが微妙に押し合って永遠に揺れ続ける問題がありました。これはrestitution（反発係数）とfriction（摩擦係数）のバランスが悪いと起きます。

何度もプレイしながら数値を調整した結果、以下の値に落ち着きました。

パラメータ値意図
restitution（反発係数）0.22ほど良い弾み。0に近づけるとプラスチックっぽく、大きすぎると跳ね回る
friction（摩擦係数）0.65転がりすぎを防ぎ、積み重なりを安定させる
frictionAir（空気抵抗）0.025落下速度を少し緩め、操作感をやわらかくする
density（密度）0.003軽すぎると浮き、重すぎると落下が速すぎる

特にfrictionAirの値が操作感に大きく影響することが分かりました。スマートフォンで指を離してからどうぶつが落ちるまでのわずかな時間に、ユーザーが「ちゃんと操作できている」と感じるかどうかが変わります。0に近づけると落下がシャープで爽快になりますが、入力のシビアさが増して子ども向けには難しくなりました。

3. 合体処理のタイミング問題

Matter.jsの衝突イベントは「物体が重なった瞬間」に発火しますが、その瞬間に即座に2つのボディを削除して1つの新しいボディを生成すると、物理ワールドが不安定になるケースがありました。

解決策として、合体処理をsetTimeout(..., 30)で30ミリ秒遅延させています。この一手間で、物理ワールドが現在のフレームを処理し終えてから変更が加わるようになり、安定しました。

Events.on(engine, 'collisionStart', e => { for (const { bodyA, bodyB } of e.pairs) { if (bodyA.atype !== bodyB.atype) continue; bodyA.merged = bodyB.merged = true; setTimeout(() => { // 30ms後にボディ入れ替え → 物理ワールドが安定 World.remove(world, bodyA); World.remove(world, bodyB); const newBody = mkAnimal(midX, midY, bodyA.atype + 1); Body.setVelocity(newBody, { x: 0, y: -4 }); }, 30); } });

描画はMatter.jsのRendererを使わなかった理由

Matter.jsにはデフォルトのレンダラーが付属していますが、どうぶつドロップでは使っていません。理由は絵文字の描画です。デフォルトレンダラーはCanvas APIのシンプルな図形描画を前提としており、絵文字を各ボディの中央に表示するカスタマイズが難しいためです。

代わりに、Matter.jsを物理計算エンジンとして使い、毎フレームrequestAnimationFrameで自前のCanvas描画ループを回すアーキテクチャにしました。world.bodiesから各どうぶつの位置と角度を取得し、その座標に合わせて絵文字と円を描画しています。

// 物理計算（Matter.js） Runner.run(runner, engine); // 描画（自前のCanvas） function loop(now) { for (const b of world.bodies) { if (b.label !== 'animal') continue; ctx.save(); ctx.translate(b.position.x, b.position.y); ctx.rotate(b.angle); drawAnimal(0, 0, b.circleRadius, b.atype); ctx.restore(); } requestAnimationFrame(loop); }

この構成により、物理シミュレーションの精度を保ちながら、絵文字を回転させたりグラデーション円を描いたりといった自由な演出が可能になりました。

💡 まとめ
  • 物理エンジンは自前実装のトンネリング・スタック問題を解決するために導入した
  • Matter.jsを選んだ決め手は「外部依存ゼロ」と「情報量の多さ」
  • 床の厚み・positionIterations増加でトンネリングを対策した
  • 摩擦・反発係数は操作感に直結するため、実際のプレイで繰り返し調整した
  • 描画は自前のCanvasループを使い、Matter.jsは物理計算専用に分離した
